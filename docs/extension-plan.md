# 挑战加分项分步开发计划

状态：**规划，四项尚未实现。** 当前可运行版本已完成六项基础课程要求。本文用于按小步骤继续学习，不把设计方案当作已交付功能。

完整的现有系统演示命令见 [README](../README.md)。本阶段建议按“双龟前置改造 → 双龟 → 抢占 → 超时返航 → 轨迹对比”推进。

## 每个小步骤怎么学习与提交

1. 先写一句话说明本次新增行为，限制在一个可验证的小目标。
2. 修改一个模块，理解输入、状态变化与输出，不一次覆盖整套系统。
3. 先验证原单龟流程没被破坏，再运行新增场景。
4. 记录终端命令、关键日志、海龟现象；涉及任务切换时确认最终状态和零速度。
5. 完成一个验收点后再提交 Git，README 中仍未实现的项目保持未完成。

这些拓展涉及异步任务状态，不能仅以“海龟动了”判断正确；需要核对哪个目标活动、哪个话题被控制、旧任务如何结束。

## 第一阶段：双龟巡逻

### A1：让一个服务端可以选择海龟

改动文件：`patrol_server.py`。

1. 添加字符串参数 `turtle_name`，默认 `turtle1`。
2. 创建订阅/发布器前读取参数，构造 `/<turtle_name>/pose` 与 `/<turtle_name>/cmd_vel`。
3. 替换当前两个写死的话题路径，其他导航算法先保持不变。
4. 先只运行默认 turtle1，完成三航点巡逻，证明默认行为不变。

验收：默认配置仍完成三航点；查询节点信息能看到实际选择的 pose/cmd_vel 话题。

这是开始编码的第一小步，不需要先启动第二个服务端。

### A2：划清两个服务端的身份

改动文件：`patrol_server.py`、`patrol_client.py`，随后再扩展 Launch。

1. 为两套服务端/客户端分配不同命名空间，例如 `/robot1` 和 `/robot2`。
2. Action 保持相对名称 `patrol`，解析为 `/robot1/patrol`、`/robot2/patrol`。
3. 审查单实例锁：当前锁只按用户和通信域生成，会阻止第二实例。把锁身份扩展为域、节点命名空间/名称及控制对象，保留防止同一控制对象被重复实例控制的检查。
4. 明确仿真对象名称与 ROS 节点命名空间的区别：`robot1` 是节点分组，`turtle1` 是 turtlesim 内的对象。
5. 验证只启动 robot1 时仍可巡逻，重复启动同一身份仍被保护。

验收：两个 Action 地址互不冲突，实际速度发布仍分别指向 turtle1/turtle2；不要把锁简单删除了事。

### A3：生成第二只海龟，再分别控制

1. 使用 `/spawn` 服务创建命名为 turtle2 的海龟，为两只海龟选不同初始位置。
2. 先验证 turtle1 单独运动时 turtle2 静止，再反向验证。
3. 再启动两套客户端，各自使用不同路线。
4. 分别取消一只海龟的任务，确认另一只不受影响。

验收：每只海龟的 Action 结果、反馈、速度话题均可独立追踪，没有交叉控制。

### A4：封装双龟 Launch

新建独立的双龟 Launch 文件，保留基础 `patrol.launch.py`。
让模拟器先提供 spawn 服务，再生成 turtle2；各服务端收到各自位姿后才开放 Action。使用实际就绪条件，不靠任意固定 sleep 猜测启动顺序。

验收：一条新命令启动双龟演示；退出后无两套服务端残留。完成后才向 README 写入实际命令。

## 第二阶段：多任务抢占

### B1：定义新旧任务的结束语义

当前忙碌分支会中止新任务，而不是抢占旧任务。先定义：

- 新的有效 Goal 到来后，旧任务停止控制并发布零速度，再允许新任务控制。
- 标准 ROS2 Action 没有单独的 PREEMPTED 结果状态。可把被抢占旧任务标记为 ABORTED，并在日志/扩展结果中注明原因；显式取消仍返回 CANCELED。
- 无效新 Goal 不应先把正在执行的有效旧任务打断。
- 连续到来的多个新 Goal 采用什么策略，例如只保留最新任务，需要明确。

### B2：隔离每个任务的状态

改动主要在服务端。当前 `motion_future`、`target_point`、活动句柄都属于全局共享状态，不能简单覆盖。

1. 为每次任务分配身份/代次，并保存它自己的等待对象和结果计数。
2. 新任务先请求旧任务停止，等待控制权交接完成。
3. 旧任务的 `finally` 只能清理自己仍拥有的控制状态，不能给新任务发停车或清空新目标。
4. 用回调、Future 和执行器协调，不加阻塞 sleep 等待旧任务结束。

### B3：逐场景验收

先单龟测试：旧路线执行中发送新路线，确认旧任务结束、新任务完成。再测试转向时抢占、前进时抢占、到达边界附近抢占、连续快速发三个目标、抢占与取消同时发生。

验收证据：旧 Goal 的最终结果、新 Goal 的反馈/最终结果、切换时停车消息，以及全程只有一个任务能发布非零控制。

## 第三阶段：单航点超时自动返航

### C1：保存返航点、增加单段计时

改动主要在服务端。

1. 开始一项新任务时保存起始 pose，作为本任务返航点。不是把 `(0,0)` 直接当成目标。
2. 添加服务端参数 `waypoint_timeout`，默认30秒。
3. 每进入一个新航点重置计时；使用同一明确的时间源，不把整个任务计时误当成单航点计时。
4. 明确客户端 `cancel_timeout` 是独立的整体截止时间，不能先到期导致返航演示被客户端取消。

### C2：增加返航状态

先实现“单航点超时 → 零速度 → 终止原巡逻并记录完成数量”，再复用导航逻辑返回记录的起点。

设计时明确：

- 原任务失败与返航成功分别怎样报告。若原 Goal 已终止，就不能继续向已结束的 Goal 发布反馈或第二次设置终态。
- 如需客户端看到返航进度，可选择独立返航 Action/状态话题，或在任务未终止前切入返航并扩展结果字段；这两种方案要先选定并与验收语义对齐。
- 用户显式取消通常应停车，而不是突然自动返航。
- 返航本身也要有超时与失败处理，不能失败后无限再次触发返航。
- 返航中收到新 Goal 时采用拒绝、排队还是抢占，应明确。

### C3：制造可控的超时

在 turtlesim 中可降低速度上限、使用较远但仍有效的目标，或缩短测试用单航点超时，制造可复现的触发条件。不要使用越界目标绕过输入校验。

验收：正常巡逻不返航；单段超时能触发；返航到保存起点附近停车；结果和日志没有把“巡逻未完成、返航成功”误报成整条巡逻成功。

## 第四阶段：同参数两轮 bag 轨迹对比

### D1：建立可比的两次实验

1. 固定同一份代码、速度、路线、初始 x/y/theta 和超时设置。
2. 每轮都先开录制，再启动巡逻；结束后停止录制。
3. 第一轮结束后停止控制节点并重新创建初始海龟，再录第二轮。
4. 使用不同的 bag 目录保存，记录两次参数和最终结果。

先比较“同配置两次闭环巡逻”；后续可再比较“原始记录与同一指令回放”。这两类实验含义不同，应分别报告。

### D2：先读数据，再画轨迹

计划新增 `tools/compare_bags.py`，目前尚无该脚本。

1. 用 rosbag2 API 读取 pose 消息和时间戳，导出可检查的数据。
2. 绘制两轮 x-y 路径并标出航点与起终点。
3. 把每轮起始运动时刻定义为相对时间0，避免拿绝对录制时间相减。
4. 对齐有效运动区间，把轨迹插值到公共时间点后再计算位置误差。
5. 角度误差做归一化，不直接相减跨越 ±π 的 theta。

验收：输出两轮时长、样本数量、轨迹叠加图、终点差、位置误差均值/RMSE/最大值，并说明对齐方法。

### D3：解释差异

模型确定性不代表 ROS 消息发现、回调调度、定时器执行、采样时间和闭环控制起点每轮都一致。不要逐条按消息编号比较，也不要预设浮点数据必须完全相同。

真实机器人还会受到轮胎打滑、地面变化、电机差异、传感器噪声、定位漂移、外界障碍物与通信延迟影响。因此应先给出数据与误差解释，再讨论是否需要优化。
